# Creating a new project

Step by step guide for agents: a new Django + Next.js project on this deploy module, from an empty
directory to production with Sentry. FastAPI-only differences are at the end.

Read `README.md` (deploy.json, commands) and `CLAUDE.md` of this repo first. Everything below is run
from the project root; `pc` is `./deploy/dc`.

## 0. Decide and ask

Ask the user before starting, do not invent:

- **Project name** (`PROJECT_NAME`): lowercase, `[a-z0-9]`, used for container, image, bucket,
  database and Sentry project names (`<name>-django`, `<name>-media`, `<name>-backend`, …).
  It may differ from the domain (e.g. `hcmanager` lives at `rhouse.grey.one`).
- **Production domain** (`PROJECT_DOMAIN`) and **dev domain** (by convention `dev.<domain>`).
- **GitHub repository** (by convention `github.com/grey0ne/<name>`, created by the user).
- Which components: Django + Next.js (default), FastAPI, Celery, Centrifugo (see `deploy.json`).

What is automated and what is not:

| Step | How |
|---|---|
| Repository skeleton, submodules, env files | by hand (this guide) |
| Dev certificates, `/etc/hosts`, dev nginx, compose | `pc up` |
| DNS A record, Postgres database, droplet | DigitalOcean console or `pc initinfra` (careful, see 4.2) |
| Spaces buckets and their CDN subdomains (`static.`, `media.`) | DigitalOcean console, by hand |
| Sentry projects | Sentry UI or Sentry MCP (section 5) |
| Certificates, images, migrations, Swarm stack, prod nginx, Sentry release | `pc deployprod` |

## 1. Repository skeleton

Do not use the old `project_template` repo: it has the outdated `backend/` / `spa/` layout. Copy
the structure from the most recently updated project that uses the same components and remove its
domain code. Expected layout (see `CLAUDE.md`):

```
<project>/
  deploy/                 submodule github.com/grey0ne/deploy
  deploy.json
  environment/            env.base + version committed; env.dev, env.prod gitignored
  django_backend/         django_utils submodule inside
  nextjs_frontend/        next_utils submodule inside
  .gitignore  .github/dependabot.yml  .devcontainer/devcontainer.json  CLAUDE.md  README.md
```

```bash
git init
git submodule add git@github.com:grey0ne/deploy.git deploy
git submodule add git@github.com:grey0ne/django_utils.git django_backend/django_utils
git submodule add git@github.com:grey0ne/next_utils.git nextjs_frontend/next_utils
```

`.gitignore` must contain at least: `environment/env.dev`, `environment/env.prod`, `.env`,
`backend_data`, `django_backend/collected_static/`, `nextjs_frontend/node_modules`,
`nextjs_frontend/.next`, `nextjs_frontend/next-env.d.ts` (generated by Next.js, differs between
`dev` and `build`), `nextjs_frontend/tsconfig.tsbuildinfo`. The generated compose files are ignored
inside this submodule.

`.github/dependabot.yml` directories: `/` (devcontainers), `/nextjs_frontend` (npm),
`/django_backend` (pip).

### deploy.json

```json
{
  "django": { "worker_count": 2 },
  "nextjs": {},
  "services": { "celery": { "enabled": false }, "centrifugo": { "enabled": false } },
  "dev": { "postgres": { "enabled": true }, "minio": { "enabled": true } }
}
```

### Django (`django_backend/`)

- `pyproject.toml` (Poetry, `package-mode = false`): the Python constraint must accept the version
  of `docker/Dockerfile.django*` in this repo. Copy dependencies from a current project.
- `install-dependencies.sh`: apt packages installed into the image (`echo "No dependencies"`
  when none). Adding a package needs an image rebuild (`pc build django`) and changes production.
- `manage.py`, `application/{settings,urls,api,admin,asgi,worker}.py`:
  - `settings.py` starts with `from django_utils.base_settings import *` and defines
    `PROJECT_APPS`, `INSTALLED_APPS` (`social_django` is required: base settings reference its
    context processors).
  - Add `LOGGING` that sends `django.request` errors and warnings to the console. Without it and
    without Sentry, production 500 errors leave no trace: with `DEBUG` off Django sends them only
    to `mail_admins`.
- A `users` app with `User` model is required: base settings set `AUTH_USER_MODEL = 'users.User'`
  and `django_utils.auth` imports `users.models.User`. Optional `users/frontend_user_data.py`
  with `async def get_user_data(request)` fills the `user_data` cookie for the frontend.
- Generate the initial migrations in the container (`pc django makemigrations`), never copy them.
- `tests/settings.py` (`from application.settings import *`) + `tests/conftest.py`;
  pytest is configured in `pyproject.toml` (`DJANGO_SETTINGS_MODULE = "tests.settings"`).

### Next.js (`nextjs_frontend/`)

- Copy `package.json` (rename), `next.config.ts`, `tsconfig.json`, `eslint.config.mjs` (flat
  config, ESLint 9+), `proxy.ts`, `global.ts`, `constants.ts` (`ENABLED_LOCALES`), `i18n/`,
  `instrumentation*.ts`, `sentry.*.config.ts`, `app/theme.ts`, `app/global-error.tsx`,
  `app/[locale]/{layout,page,not-found}.tsx`, `messages/{ru,en}.json`.
- The frontend DSN comes from `NEXT_PUBLIC_SENTRY_FRONTEND_DSN`. `next.config.ts` uploads source
  maps to the Sentry project `${PROJECT_NAME}-frontend` during `next build`: the production image
  build gets `PROJECT_NAME`, `SENTRY_ORG` and `SENTRY_RELEASE` (the new version) as build args and
  `SENTRY_RELEASE_TOKEN` as a build secret (never stored in the image). Without the token the build
  succeeds, but frontend errors reach Sentry with minified stack traces.
- `api/apiTypes.ts` is generated (`pc generatetypes`), never written by hand.

### environment/

`env.base` (committed, no secrets):

```
PROJECT_NAME=<name>
PROJECT_DOMAIN=<production domain>
REGISTRY_HOSTNAME=ghcr.io
REGISTRY_NAMESPACE=grey0ne
SSL_CERTS_DIR=~/ssl_certs
NGINX_CONFIG_DIR=~/nginx_configs
DJANGO_WORKER_COUNT=2
```

`version`: `0.0` (bumped and committed by `deployprod`).

`env.dev` (gitignored):

```
DJANGO_SECRET_KEY=<random, python -c "import secrets; print(secrets.token_urlsafe(50))">
DJANGO_DEBUG=True
PROJECT_DOMAIN=dev.<domain>
NODE_ENV=development
S3_DOMAIN=dev.<domain>
S3_SIGNATURE_VERSION=s3v4
S3_ENDPOINT_URL=http://<name>-minio:9000
S3_MEDIA_BUCKET=<name>-media
S3_ACL=public-read
NEXT_TELEMETRY_DISABLED=1
```

- `S3_SIGNATURE_VERSION=s3v4`: current MinIO rejects writes signed with the legacy `s3` (v2)
  signature (SignatureDoesNotMatch). Older projects still have `s3` and cannot upload in dev.
- `DJANGO_DEBUG` is parsed with `bool()`: any non-empty value, including `False`, enables
  debug. To disable it leave the variable out (production does not set it).

## 2. Development environment

```bash
pc up                  # first run asks for sudo: dev certificate, /etc/hosts, balancer config
pc rebuild             # images + npm install inside the nextjs container
pc migrate
pc s3createdevbucket   # media bucket in MinIO
pc generatetypes       # after the backend is running
pc test
```

Open `https://dev.<domain>`. Never run `npm install` / `next build` on the macOS host:
`nextjs_frontend` is bind-mounted into the Linux container and shares `node_modules`.

If the project directory is renamed, recreate the containers (`pc rebuild`): running containers
keep bind mounts of the old path and silently show stale code.

## 3. Commit and push

Commit the skeleton (submodules pinned to commits that exist on GitHub) and push to the user's
repository before the first deploy: `deployprod` commits `environment/version` itself.

## 4. Production infrastructure

### 4.1 Current setup

All production projects share one server (a Docker Swarm node behind one nginx balancer) and one
DigitalOcean managed Postgres cluster; each project has its own database. Find the current
values from an existing project instead of hardcoding them:

```bash
dig +short <domain of an existing project>                 # server IP
grep -E '^DATABASE_(HOST|PORT|USER)=' ../<existing project>/environment/env.prod
ssh root@<existing domain> 'docker node ls'                # node / droplet name
```

The balancer is shared: a broken nginx config or a missing certificate of one project stops
nginx for every site on the server. `certprod` / `deployprod` check certificates before
touching nginx; do not edit the balancer by hand.

### 4.2 Server, DNS, database

New project on the existing server (the usual case):

1. DNS: an A record `<domain>` → server IP (DigitalOcean DNS or the registrar of the domain).
2. Database: create `<name>` (or `DATABASE_NAME`) in the existing cluster in the DigitalOcean
   console. Projects use the cluster admin user: DigitalOcean API cannot grant privileges to
   other users.
3. Do **not** run `initprod` / `deploybalancer`: they reinstall Docker and the shared balancer.

`pc initinfra` automates DNS + database + firewall, but by default creates a new droplet
`<name>-app`. To reuse the existing server set in `env.prod`: `DO_TOKEN`, `DO_DROPLET_NAME=<existing
droplet name>`, `DATABASE_USER=<cluster admin user>` (`PG_CLUSTER_NAME` defaults to
`communal-db`). It writes `DATABASE_HOST` and, for a new user, `DATABASE_PASSWORD` into `env.prod`.
Confirm with the user before running it: it creates paid resources.

A project on a new dedicated server: `initinfra` (droplet, DNS, database), then `initprod`
(Docker, balancer, certificates), then deploy.

### 4.3 Spaces (S3) buckets

Create in the same Spaces region as the other projects (`ams3`):

| Bucket | Access | CDN custom subdomain |
|---|---|---|
| `<name>-static` | public | `static.<domain>` |
| `<name>-media` | public (`S3_ACL=public-read`) | `media.<domain>` |
| `<name>-private` (only if the project stores personal files) | private, no CDN | — |

Django uses `STATIC_URL = https://static.<domain>/` and `media.<domain>` for media
(`S3_STATIC_DOMAIN` / `S3_MEDIA_DOMAIN` override them). Enable the CDN for the public buckets with
the custom subdomain: DigitalOcean creates the CNAME `static.<domain>` →
`<bucket>.ams3.cdn.digitaloceanspaces.com` and its certificate (the subdomain's DNS zone must be in
DigitalOcean; otherwise create the CNAME at the registrar). `deployprod` issues certificates only
for `PROJECT_DOMAIN`, `EXTRA_DOMAINS` and `centrifugo.<domain>`, not for these subdomains.
A private bucket must never be public: MinIO and Spaces serve objects by bucket policy, private
files are served through permission checked application endpoints.

### 4.4 env.prod

```
DJANGO_SECRET_KEY=<new random value, not the dev one>
NODE_ENV=production

REGISTRY_USERNAME=<GitHub user>
REGISTRY_PASSWORD=<GitHub token with write:packages; same as in other projects>

DATABASE_NAME=<name>
DATABASE_USER=<cluster admin user>
DATABASE_PASSWORD=…
DATABASE_HOST=…
DATABASE_PORT=25060

S3_ACCESS_KEY_ID=…
S3_SECRET_KEY=…
S3_ENDPOINT_URL=https://ams3.digitaloceanspaces.com
S3_SIGNATURE_VERSION=v4
S3_ACL=public-read
S3_MEDIA_BUCKET=<name>-media
S3_STATIC_BUCKET=<name>-static

SENTRY_ORG=grey
SENTRY_DSN=<DSN of <name>-backend>
NEXT_PUBLIC_SENTRY_FRONTEND_DSN=<DSN of <name>-frontend>
SENTRY_RELEASE_TOKEN=<organization token, same in all projects>
```

Optional: `EXTRA_DOMAINS` (comma separated, served by the default backend),
`NEXT_PUBLIC_GTAG`, `NEXT_PUBLIC_YM_ID`, project specific keys (OAuth clients, …).
`PROJECT_VERSION` / `NEXT_PUBLIC_VERSION` are written (added if missing) by `deployprod`.
Shared credentials (registry, Spaces keys, database, Sentry release token) can be copied from
another project's `env.prod` with the user's consent; never print them or commit them.

`NEXT_PUBLIC_*` values are baked into the frontend at build time (`deployprod` writes them to
`nextjs_frontend/.env` before `next build`): changing them needs a new deploy.

## 5. Sentry

Conventions: organization `grey`, team `metagame`, two projects per application:

| Project | Platform | Env variable |
|---|---|---|
| `<name>-backend` | `python-django` | `SENTRY_DSN` |
| `<name>-frontend` | `javascript-nextjs` | `NEXT_PUBLIC_SENTRY_FRONTEND_DSN` |

The names must match `SENTRY_PROJECTS` (default `<name>-frontend,<name>-backend`): `deployprod`
creates a release with the new version in both projects.

With the Sentry MCP plugin:

1. `find_organizations` → `grey` (region `https://us.sentry.io`), `find_teams` → `metagame`.
2. `create_project` (organizationSlug `grey`, teamSlug `metagame`, `name`/`slug`, `platform`) for
   both projects; the response contains the DSN (`find_dsns` returns it later).
   A 403 "Your organization has disabled this feature for members" means the organization setting
   *Let Members Create Projects* is off: the MCP token acts as a member. Ask the user to enable it
   or to create the projects in the UI.
3. Sentry creates the alert "Send a notification for high priority issues" for each project with
   a 0 minute interval; the other projects use 30 minutes:
   `update_alert_rule(ruleIdOrName=<id>, frequencyMinutes=30)` (`find_alert_rules` with
   `projectSlug` gives the id).
4. Write the DSNs and `SENTRY_ORG=grey` into `env.prod`.

Without the plugin: create the same projects in the Sentry UI and copy the DSNs from
Project Settings → Client Keys.

`django_utils.base_settings` initialises Sentry when `SENTRY_DSN` is set; the frontend SDK is
configured by the copied `instrumentation*.ts` / `sentry.*.config.ts`.

## 6. First deploy

Prerequisites on the developer machine: Docker, `python3.15`, ssh access as `root@<domain>`
(the same key as for the other projects), DNS of `<domain>` already resolving to the server
(certbot uses an HTTP challenge).

```bash
pc deployprod
```

It checks the registry config, issues missing certificates, bumps and commits the version,
builds `linux/amd64` images and pushes them to ghcr.io, creates the Sentry release, collects
Django static into `<name>-static`, renders and copies the Swarm compose and env files, runs
migrations in the new image, updates the stack and reloads nginx. Push the version commit
afterwards.

One-off production commands and checks:

```bash
pc logsprod django          # also: nextjs, celery, …
pc djangoprod <command>     # manage.py in the production image, e.g. createsuperuser
pc djangoprod showmigrations
curl -sI https://<domain>/
```

Project specific one-off setup (e.g. a private bucket created by a management command) goes to the
project's README and CLAUDE.md.

## 7. Checklist

- [ ] Name, domains, repository agreed with the user
- [ ] Skeleton committed, submodules pinned to commits that exist on GitHub, pushed
- [ ] `pc up`, `pc migrate`, `pc test`, `pc generatetypes` work; site opens on `dev.<domain>`
- [ ] DNS A record for `<domain>`; database in the cluster
- [ ] Buckets `<name>-static`, `<name>-media` with CDN subdomains `static.` / `media.`
- [ ] `env.prod` filled (section 4.4), no secrets committed
- [ ] Sentry projects `<name>-backend` / `<name>-frontend`, alert interval 30 minutes, DSNs in `env.prod`
- [ ] `pc deployprod` passed, version commit pushed
- [ ] Site opens on `https://<domain>`, static loads from `static.<domain>`, a test error reaches Sentry
- [ ] `LOGGING` sends request errors to the console (`pc logsprod django` shows tracebacks)
- [ ] Project CLAUDE.md / README describe the project specific parts

## FastAPI projects

Same flow with `fastapi_backend/` and the `fastapi` section of `deploy.json` (see README): no
`django_utils`, migrations come from `fastapi.migrate_command`, one-off commands run with
`pc fastapiprod <command>`, and there is no `django_utils` to initialise Sentry: configure the SDK
in the application (Sentry platform `python-fastapi` for the backend project). Static files and the
Django `collectstatic` step are absent.
